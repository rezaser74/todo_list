مفهوم **REST API** یکی از مهم‌ترین ستون‌های فقرات توسعه بک‌اند و وب مدرن است. برای اینکه درک عمیق و کاربردی پیدا کنی، آن را پله‌پله و با مثال‌های واقعی بررسی می‌کنیم.

---

## ۱. REST API چیست؟ (به زبان ساده اما عمیق)

کلمه **REST** مخفف *Representational State Transfer* است. REST یک «پروتکل» یا یک «زبان برنامه‌نویسی» نیست؛ بلکه **یک سبک معماری (Architectural Style)** و مجموعه‌ای از استانداردها برای طراحی ارتباط بین کلاینت (مثل اپلیکیشن موبایل، فرانت‌اند وب) و سرور (بک‌اند) است.

### تمثیل منوی رستوران:

تصور کن وارد یک رستوران شده‌ای:

* **شما (Client):** می‌خواهی غذا سفارش بدهی.
* **گارسون (REST API):** درخواست (Request) شما را می‌گیرد، به آشپزخانه می‌برد و پاسخ (Response) را همراه با غذا برای شما می‌آورد.
* **آشپزخانه (Server & Database):** اطلاعات و دیتا را پردازش و آماده می‌کند.

اگر استاندارد REST وجود نداشت، هر بک‌اندنویسی به روش عجیب خودش API می‌نوشت و اتصال فرانت‌اند به بک‌اند تبدیل به یک کابوس می‌شد. REST آمد تا یک **زبان مشترک جهانی** ایجاد کند.

---

## ۲. اصطلاحات و قواعد اصلی REST

برای درک عمیق، باید چند قاعده ذهنی را جا بیندازی:

### ۱. منبع-محور بودن (Resource-Oriented)

در REST همه چیز یک **منبع (Resource)** است. منبع می‌تواند کاربر، محصول، سفارش یا مقاله باشد.
آدرس‌ها (URL) در REST باید اسم (Plural Noun) باشند، نه فعل!

* ❌ **اشتباه:** `[https://api.com/getUserData](https://api.com/getUserData)` یا `[https://api.com/deleteProduct](https://api.com/deleteProduct)`
* ✅ **درست (RESTful):** `[https://api.com/users](https://api.com/users)` یا `[https://api.com/products](https://api.com/products)`

### ۲. بی‌وضعیت بودن (Statelessness)

یکی از مهم‌ترین اصول REST این است که سرور **هیچ وضعیتی (State) از نشست‌های قبلی کلاینت را ذخیره نمی‌کند**.
هر درخواستی که کلاینت می‌فرستد، باید کامل باشد و تمام اطلاعات لازم (مثل توکن احراز هویت) را در خود داشته باشد تا سرور متوجه شود او کیست.

---

## ۳. متدهای اصلی HTTP (افعال ارتباطی)

اگر URLها «اسم» هستند، متدهای HTTP نقش «فعل» را بازی می‌کنند تا مشخص کنند چه عملیاتی باید روی منبع انجام شود (مفهوم **CRUD**):

| متد (HTTP Method) | مفهوم CRUD | کاربری | مثال آدرس |
| --- | --- | --- | --- |
| **GET** | Read | دریافت اطلاعات (بدون تغییر در سرور) | `GET /api/v1/users` (دریافت لیست کاربران) |
| **POST** | Create | ایجاد یک منبع جدید | `POST /api/v1/users` (ثبت کاربر جدید) |
| **PUT** | Update | جایگزینی کامل یک منبع موجود | `PUT /api/v1/users/42` (ویرایش کامل کاربر کد ۴۲) |
| **PATCH** | Update | ویرایش جزئی (فقط تغییر بخش‌هایی از دیتا) | `PATCH /api/v1/users/42` (مثلا فقط تغییر ایمیل) |
| **DELETE** | Delete | حذف یک منبع | `DELETE /api/v1/users/42` (حذف کاربر کد ۴۲) |

---

## ۴. کدهای وضعیت (Status Codes)

وقتی کلاینت درخواستی می‌فرستد، سرور با یک کد سه رقمی پاسخ می‌دهد تا وضعیت درخواست مشخص شود. این کدها ۵ رده اصلی دارند:

### ۱xx: اطلاع‌رسانی (Informational)

کمتر در کار روزمره مستقیم با آن‌ها مواجه می‌شوی (درخواست دریافت شده و در حال پردازش است).

### ۲xx: موفقیت (Success)

* **`200 OK`:** درخواست با موفقیت انجام شد (عموما برای GET, PUT, PATCH).
* **`201 Created`:** منبع جدید با موفقیت ساخته شد (پاسخ استاندارد برای POST).
* **`204 No Content`:** عملیات موفق بود اما پیاام/دیتا در بدنه پاسخ وجود ندارد (عموما برای DELETE).

### ۳xx: تغییر مسیر (Redirection)

* **`301 Moved Permanently`:** آدرس به جای دیگری منتقل شده است.

### ۴xx: خطای کلاینت (Client Error) - اشکال از سمت فرانت/کاربر است

* **`400 Bad Request`:** فرمت ورودی اشتباه است (مثلا ایمیل بدون `@`).
* **`401 Unauthorized`:** کاربر احراز هویت نشده (لاگین نکرده یا توکن منقضی شده).
* **`403 Forbidden`:** کاربر لاگین کرده اما دسترسی (Permission) به این منبع را ندارد (مثلا کاربر عادی می‌خواهد دیتا بیس مدیر را ببیند).
* **`404 Not Found`:** منبع یا آدرس مورد نظر پیدا نشد.
* **`409 Conflict`:** تداخل در اطلاعات (مثلا ثبت‌نام با ایمیلی که قبلا در سیستم وجود داشته).

### ۵xx: خطای سرور (Server Error) - اشکال از سمت بک‌اند است

* **`500 Internal Server Error`:** کد بک‌اند به باگ خورده یا کرش کرده است.
* **`502 Bad Gateway` / `503 Service Unavailable`:** سرور زیر فشار است، داون شده یا ارتباط دیتابیس قطعه.

## ۵. کجاها از REST API استفاده می‌شود؟

امروزه تقریباً در تمام برنامه‌های نرم‌افزاری دنیا REST API حضور دارد:

1. **ارتباط Single Page Applications (SPA) با بک‌اند:** معماری‌های مدرن که فرانت‌اند (React, Vue, Angular) کاملاً از بک‌اند (Node.js, Python, Laravel, Go) جداست.
2. **اپلیکیشن‌های موبایل (Android/iOS):** موبایل‌ها برای دریافت دیتا از دیتابیس مرکزی از REST API استفاده می‌کنند.
3. **معماری میکروفرانت/میکروسرویس (Microservices):** زمانی که بک‌اند به ۱۰ سرویس کوچک‌تر تقسیم شده و این سرویس‌ها باید با هم حرف بزنند.
4. **ارتباط با سرویس‌های سوم‌شخص (Third-Party):**
* اتصال به درگاه پرداخت (مثل زرین‌پال یا Stripe).
* ارسال پیامک (پنل‌های SMS).
* دریافت اطلاعات هواشناسی یا نقشه گوگل.

## جمع‌بندی تصویری از یک سناریوی واقعی

تصور کن می‌خواهی یک محصول جدید اضافه کنی:

1. **فرانت‌اند:** یک درخواست `POST` به `[https://api.shop.com/v1/products](https://api.shop.com/v1/products)` می‌فرستد.
2. **بدنه درخواست (Body):** اطلاعات محصول مثل نام و قیمت به فرمت JSON ارسال می‌شود.
3. **هدر (Header):** شامل `Authorization: Bearer <TOKEN>` است (برای اثبات لاگین بودن).
4. **پاسخ سرور:** اگر همه‌چیز درست باشد، سرور کد `201 Created` را به همراه مشخصات محصول ساخته‌شده برمی‌گرداند.

---

آیا تمایل داری روی چگونگی **ساختار هدرها (Headers)** و **فرمت داده‌ها (JSON)** بیشتر عمیق شویم، یا دوست داری یک نمونه کد واقعی از پیاده‌سازی آن را با هم بررسی کنیم؟
