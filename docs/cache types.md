# 📑 بررسی جامع کشینگ در لایه‌های نرم‌افزار (Comprehensive Backend Caching Architecture)

کشینگ (Caching) عبارت است از تکنیک **ذخیره‌سازی موقت داده‌ها** در یک لایه‌ی حافظه‌ی سریع‌تر (یکپارچه با نرخ تاخیر یا Latency بسیار پایین)، با هدف کاهش بار محاسباتی (Compute Overhead) و ورودی/خروجی دیسک (Disk I/O) در لایه‌های پایین‌تر.

```
[ HTTP Client / Browser ] 
        │
        ▼ (1. Client/HTTP Cache)
[ Edge Network / CDN ] 
        │
        ▼ (2. Edge Cache)
[ Web / Application Server ] 
        │
        ▼ (3. Application In-Memory Cache: Redis / Memcached)
[ Database Engine ] 
        │
        ▼ (4. Database Buffer Pool / Page Cache)
[ Disk Storage ]

```

---

## 🔬 کالبدشکافی علمی لایه‌های چهارگانه کشینگ (The 4 Layers of Caching)

### ۱. کش سمت کلاینت و مرورگر (Client & HTTP Caching)

* **مکانیسم عملکرد:** بر اساس استانداردهای RFC 9111 HTTP Caching، مرورگر پاسخ‌ها را بر اساس هدرهای کنترل‌کننده در حافظه محلی (Disk/Memory Cache) ذخیره می‌کند.
* **مولفه‌های کلیدی:**
* **`Cache-Control`:** تعیین سیاست کش با کلیدواژه‌هایی مثل `public`, `private`, `no-cache`, `max-age`.
* **`ETag` (Entity Tag) / `If-None-Match`:** مکانیزم اعتبارسنجی شرطی (Validation). سرور یک هش از محتوا برمی‌گرداند؛ اگر داده تغییر نکرده باشد، پاسخ `304 Not Modified` بدون ارسال مجدد بدنه داده صادر می‌شود.



---

### ۲. کش در شبکه لبه (Edge & CDN Caching)

* **مکانیسم عملکرد:** شبکه توزیع محتوا (CDN) با داشتن سرورهای متعدد در لبه‌های جغرافیایی شبکه (PoPs - Points of Presence)، درخواست‌های ورودی کاربران را ایزوله و پاسخ‌های استاتیک را نزدیک به موقعیت کاربر ارائه می‌دهد.
* **مولفه‌های کلیدی:**
* کاهش شدید RTT (Round Trip Time).
* توانایی Offload کردن ترافیک سنگین شبکه از روی Origin Server.



---

### ۳. کش لایه برنامه و حافظه (Application In-Memory Caching)

* **مکانیسم عملکرد:** ذخیره‌سازی ساختارهای داده‌ای در حافظه اصلی (RAM) با نرخ دسترسی نانوثانیه‌ای/میکروثانیه‌ای به جای دسترسی میلی‌ثانیه‌ای به دیسک.
* **موتورهای اصلی:**
* **Redis:** دیتابیس In-memory با ساختار داده پیشرفته (Key-Value, Hashes, Lists, Sets)، قابلیت Persistence روی دیسک (AOF/RDB) و معماری Pub/Sub.
* **Memcached:** سیستم توزیع‌شده بسیار ساده، Multi-threaded و فوق‌العاده سریع صرفاً برای ذخیره‌سازی کلید-مقدار (Key-Value) در حافظه.



---

### ۴. کش لایه دیتابیس (Database Buffer / Page Cache)

* **مکانیسم عملکرد:** مدیریت حافظه توسط RDBMS (مثل InnoDB Buffer Pool در MySQL یا Shared Buffers در PostgreSQL).
* **مولفه‌های کلیدی:**
* دیتابیس بلوک‌های داده‌ای (Pages) پرکاربرد را روی RAM سرور دیتابیس نگه می‌دارد تا عملیات Random Disk I/O را به حداقل برساند.



---

## 🎯 ماتریس تصمیم‌گیری: کجا استفاده کنیم / کجا استفاده نکنیم؟

### ✅ مواردی که **باید** از کشینگ استفاده شود (When to Use):

1. **داده‌های با نرخ خواندن بسیار بالا و تغییرات بسیار کم (High Read / Low Write Ratio):**
* *مثال:* لیست دسته‌بندی محصولات، تنظیمات کلی سیستم، جدول کدهای پستی.


2. **محاسبات یا کوئری‌های بسیار سنگین (Heavy Computation & Aggregations):**
* *مثال:* گزارش‌های داشبورد مدیریتی، آمار محاسباتی روزانه، نتایج کوئری‌های پیچیده JOIN‌دار.


3. **محتوای استاتیک و رسانه‌ای (Static Assets):**
* *مثال:* فایل‌های JS، CSS، عکس‌ها و فونت‌ها در لایه CDN و مرورگر.


4. **مدیریت نشست‌ها و محدودسازی نرخ درخواست (Session & Rate Limiting):**
* *مثال:* ذخیره توکن‌ها، Session IDها و شمارنده‌های Rate Limit در Redis به دلیل سرعت بالا.



### ❌ مواردی که **نباید** از کشینگ استفاده شود (When NOT to Use):

1. **داده‌های مالی و با حساسیت لحظه‌ای بالا (Real-Time Financial & Critical Data):**
* *علت:* کش بودن موجودی حساب بانک یا موجودی کیف پول باعث بروز خطاهای جبران‌ناپذیر مالی (به دلیل تاخیر انقضا یا Stale Data) می‌شود.


2. **داده‌های با نرخ نوشتن بسیار بالا (High Write Volatility):**
* *علت:* اگر داده‌ای در هر ثانیه چند بار تغییر کند، هزینه بروزرسانی یا باطل‌سازی مداوم کش (Cache Invalidation Overhead) از خواندن مستقیم از دیتابیس بیشتر خواهد بود.


3. **داده‌های اختصاصی و امنیتی حساس (Sensitive Personal Data):**
* *علت:* نباید اطلاعات شبا، گذرواژه‌ها یا داده‌های شخصی در لایه‌های کش عمومی یا CDN بدون رمزنگاری یا سیاست‌های سخت‌گیرانه `private` قرار گیرند.


4. **کوئری‌های یکبار مصرف یا سفارشی‌شده بر اساس پارامترهای بی‌شمار (Unique One-time Queries):**
* *علت:* اگر کوئری بر اساس ورودی‌های نامحدود کاربران تولید می‌شود و احتمال تکرار آن نزدیک به صفر است، ذخیره آن در کش فقط رم را به هدر می‌دهد (Cache Pollution).
