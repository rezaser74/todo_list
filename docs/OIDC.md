برای ساخت یک داکیومنت یا پرزنتیشن ارائه در مورد **OpenID Connect (OIDC)**، بهترین روش این است که مباحث را از **دلیل وجودی آن (Problem)** شروع کنید، سپس به **مفاهیم پایه** بپردازید و در نهایت **فلوی اجرایی و نکات امنیتی** را شرح دهید.

یک ساختار پیشنهادی و استاندارد برای داکیومنت شما به شکل زیر است:

---

## ۱. مقدمه و درک مسئله (Why OIDC?)

قبل از وارد شدن به جزییات فنی، شنونده باید بداند OIDC چه مشکلی را حل می‌کند:

* **تفاوت احراز هویت (Authentication) و مجوزدهی (Authorization):**
* **AuthN (کیستی؟):** اثبات هویت کاربر (*مثال: پاسپورت*).
* **AuthZ (چه دسترسی داری؟):** تعیین سطح دسترسی کاربر (*مثال: بلیط هواپیما*).


* **چرا OAuth 2.0 کافی نبود؟**
> OAuth 2.0 فقط برای **Authorization** طراحی شده بود (ارائه دسترسی به منابع به یک برنامه شخص ثالث). توسعه‌دهندگان سعی می‌کردند از Access Token برای تشخیص هویت استفاده کنند که باعث خطاهای امنیتی می‌شد. **OIDC لایه‌ای است که روی OAuth 2.0 قرار می‌گیرد تا احراز هویت استاندارد را اضافه کند.**



---

## ۲. نقش‌های اصلی در OIDC (Key Roles)

برای ارائه شفاف، ۳ یا ۴ بازیگر اصلی این پروتکل را معرفی کنید:

1. **End-User (کاربر نهایی):** فردی که می‌خواهد وارد سیستم شود.
2. **Relying Party - RP (کلاینت / برنامه شما):** اپلیکیشنی که کاربر می‌خواهد وارد آن شود.
3. **OpenID Provider - OP (ارائه‌دهنده هویت):** سرور مرکزی هویتی که کاربر را احراز هویت می‌کند (مثل Keycloak، Auth0، Google).

---

## ۳. توکن‌ها و ساختار داده (Core Tokens)

این بخش قلب فنی مستند شماست. باید فرق دو توکن اصلی را روشن کنید:

### مقایسه ID Token و Access Token

| ویژگی | ID Token | Access Token |
| --- | --- | --- |
| **هدف** | اثبات هویت کاربر برای کلاینت (RP) | ارائه دسترسی کلاینت به APIها (Resource Server) |
| **گیرنده اصلی (Audience)** | اپلیکیشن کلاینت شما | API / Resource Server |
| **فرمت** | همواره JWT (کدگذاری شده و شفاف) | می‌تواند JWT یا Opaque باشد |
| **محتوا** | حاوی اطلاعات کاربر (Claims) | حاوی اطلاعات دسترسی و Scopes |

### کلیم‌های مهم در ID Token (Claims):

* `iss` (Issuer): صادرکننده توکن
* `sub` (Subject): شناسه یکتای کاربر
* `aud` (Audience): گیرنده توکن (Client ID)
* `exp` (Expiration): زمان انقضا
* `nonce`: رشته تصادفی برای جلوگیری از حملات Replay

## ۴. فلوی اجرایی اصلی (Authorization Code Flow with PKCE)

این فلوی استاندارد و امن‌ترین روش برای وب‌سایت‌ها و اپلیکیشن‌های موبایل/مدرن است:

1. **درخواست ورود:** کاربر در برنامه روی "ورود" کلیک می‌کند و به OP هدایت می‌شود.
2. **احراز هویت:** کاربر نام‌کاربری و رمزعبور را در صفحه OP وارد می‌کند.
3. **دریافت کد (Authorization Code):** سرور OP کاربر را همراه با یک Authorization Code به برنامه بازمی‌گرداند.
4. **تبادل کد با توکن:** برنامه کد را به همراه Secret/PKCE به Endpoint توکن ارسال می‌کند.
5. **دریافت توکن‌ها:** سرور OP توکن‌های `ID Token` و `Access Token` را برمی‌گرداند.
6. **اعتبارسنجی:** برنامه صحت امضا و کلیم‌های ID Token را بررسی می‌کند.

---

## ۵. چک‌لیست امنیت و Best Practices

در انتهای داکیومنت، به نکات کاربردی برای تیم‌های توسعه اشاره کنید:

* **همیشه امضای JWT را سمت کلاینت بررسی کنید** (از طریق کلیدهای عمومی JWKS).
* **از PKCE (Proof Key for Code Exchange)** برای اپلیکیشن‌های SPA و موبایل استفاده کنید.
* **کلیم‌های حساس را در ID Token قرار ندهید** (فقط اطلاعات عمومی هویت).
* **از `state` و `nonce**` برای جلوگیری از حملات CSRF و Replay استفاده کنید.
